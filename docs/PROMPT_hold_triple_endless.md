# 보트리스 무한모드: 홀드와 후반 3칸 조각 구현 프롬프트

작성: 2026-10-09. 대상 프로젝트: `C:/workspace/water-sort-survival`.

이 문서는 실제 구현 작업 지시다. 현재 소스를 확인하고 **구현, 자동 검증, 브라우저 확인, 제한된 밸런스 비교, 결과 보고까지** 진행해라. 계획이나 코드 예시만 작성하고 끝내지 마라. 기본 완료 범위는 로컬 구현과 검증이다. 실행 요청에 공개 배포가 포함되어 있을 때만 기존 Pages 배포 절차를 이어서 수행한다.

## 1. 목표와 범위

보트리스는 물병 정렬을 빠르게 이어 가며 최고 기록을 갱신하는 무한모드 게임이다. 이번에는 다음 두 기능만 추가한다.

| 기능 | 역할 | 첫 구현 규칙 |
|---|---|---|
| 임시저장고, 이하 홀드 | 현재 조각을 보관하거나 보관된 조각과 교환해 다음 배치를 계획 | 슬롯 1개, 7번째 일반 병을 얻으면 해금, 성공한 배치 사이에 1회 |
| 후반 3칸 조각 | 최대 확장 이후에도 연속된 빈 공간을 준비하게 하는 압박 | 일반 병 8개 이후 새로 생성하는 조각에만 적용, 기본 확률 5%, 최대 2색 |

**색상 보너스 목표는 이번 범위에서 제외한다.** 기존 `spare`는 물을 부어 넣는 임시 잔이며, 새 홀드와 다른 기능이다. `spare`를 이름만 바꾸거나 확장형에서 다시 켜서 구현하지 마라.

병 용량 4칸, 일반 병 6→7→8개, 현재 점수 성장표와 최대 9색은 유지한다. 점수·콤보·구간 보너스를 임의로 늘리지 않는다. 스테이지, 자동 낙하, 제한 시간, 새 재화, 광고 SDK, 별도 게임 엔진이나 라이브러리는 추가하지 않는다.

홀드는 전략적인 선택을 늘리고, 3칸 조각은 그 선택에 공간 관리 부담을 더하는 가설이다. 기능이 정상 동작한다는 사실과 실제 재미·출시 적합성은 구분해서 보고한다.

현재 특히 주의할 구현은 다음과 같다.

- `isExpanding()`은 `expansion === 1`을 검사한다. 버전 숫자만 올려 기존 확장 경로를 끊지 마라.
- `sanitizeRules()`는 필드를 명시적으로 선별한다. 새 필드를 추가하되 필드가 없는 과거 규칙은 기능이 꺼진 상태로 읽는다.
- `advancePiece()`와 `growth.queue`는 확정된 미리보기를 관리한다. `growth.generation`은 배치 턴 번호와 다르다.
- `generatePiece()`의 `tailDoublePct`는 현재 `pieceMin === 1 && pieceMax === 2`일 때 동작한다. `pieceMax`를 단순히 3으로 올리면 기존 후반 생성 비율이 바뀐다.
- `checkStuck()`는 현재 조각의 길이만 검사한다. 합법적인 홀드 대안을 검사하지 않으면 아직 살 수 있는 판을 종료한다.
- 뒤집기 횟수는 버튼을 누를 때가 아니라 뒤집힌 조각을 실제 배치할 때 `flipsPlaced`에 반영한다.
- `startGame()`과 핫 리로드의 복원 경로는 현재 `S.v === 1`을 사용한다. 전체 저장 버전을 무작정 올리지 마라.
- `paintTube(cup, S.piece, r.pieceMax)` 등에서 조각 최대 길이를 UI 높이로 사용한다. 3칸 조각 추가 때문에 병 높이가 줄어들지 않게 분리한다.

수정 전 실제 작업 파일과 실행 결과를 새 비교 자료로 보존한다. 과거 `research/uiux/baseline.json`을 덮어써 엔진 해시 검사를 억지로 통과시키지 않는다. 이번 엔진 변경에서는 과거 해시 동일 검사를 완료 조건으로 사용하지 않고, 기존 규칙의 행동 동치와 새 기능 검증을 수행한다.

## 3. 규칙 버전과 적용 대상

새로 시작하는 **표준 확장형 무한모드**에 두 기능을 적용한다. 비교 실험에서는 기능별 활성 여부와 확률을 규칙으로 분리해 홀드만·3칸만·둘 다를 실행할 수 있어야 한다. 사용자에게 실험용 모드 선택이나 복잡한 조절 화면을 추가할 필요는 없다.

- 기존 확장 버전을 유지하면서 새 기능의 버전, 홀드 해금 병 수, 3칸 해금 병 수·확률·형태 정책을 명시적으로 관리한다. 이름은 기존 코드 스타일에 맞춘다.
- 새 필드가 없는 기존 표준·커스텀·일일 규칙은 두 기능을 자동으로 켜지 않는다.
- 이미 진행 중인 저장은 저장된 규칙 그대로 이어 한다. 기존 조각이나 큐를 다시 생성하지 않는다.
- 다음 새 판에서는 이전 기본 설정을 쓰던 사용자에게 새 표준 규칙을 적용한다. `wsurv.rules.custom` 등으로 명시된 커스텀 설정은 보존한다. 이전 표준 규칙과 임의의 확장형 커스텀 규칙을 구분한다.
- 일일 도전의 규칙·날짜 시드·조각 순서는 유지한다. 이번 홀드·3칸 조각을 일일 도전에 도입하지 않는다.
- `rulesSig()`에 난도에 영향을 주는 새 정책을 포함한다. 기능이 없는 기존 서명은 문자열까지 그대로 보존한다. 홀드만·3칸만·결합·확률 5%/10% 기록이 서로 섞이면 안 된다.
- 실제 병 수가 증가하거나 홀드를 사용했다고 기록 서명이 바뀌면 안 된다. 시작할 때 선택한 규칙을 기준으로 한다.

기존 최고점·페이스·별·테마·설정과 클라우드 기록 구조를 보존한다. 새 표준 규칙의 별 획득 자격도 확인하되, 임의의 실험 규칙을 전부 표준 보상 대상으로 만들지 않는다.

## 4. 홀드 엔진 계약

### 4.1 보관과 교환

홀드는 **현재 물 조각 전체를 보관하는 슬롯 하나**다. 조각을 나누거나 일부 물만 넣을 수 없고, 병에서 물을 받을 수 없으며, 홀드 조각을 병으로 직접 드래그해 넣을 수 없다. 보관된 조각을 쓰려면 현재 조각으로 교환한 뒤 기존 넣기 조작을 사용한다.

1. 실제 일반 병 수가 7개 이상이고 게임이 진행 중일 때 해금한다. 실패한 입력이나 화면 표시만으로 해금하지 않는다.
2. 홀드가 비어 있을 때 사용하면 현재 조각을 보관하고 확정된 큐의 첫 조각을 현재 조각으로 꺼낸다. 필요한 만큼만 미리보기를 보충한다.
3. 홀드에 조각이 있으면 현재 조각과 보관된 조각을 교환한다. 큐를 이동하거나 생성 번호를 소비하지 않는다.
4. 한 번 사용하면 잠긴다. **현재 조각을 병에 성공적으로 넣었을 때만 다시 사용 가능**해진다.
5. 붓기, 뒤집기, 실패한 넣기, 렌더링, 설정·언어 변경으로 사용권이 돌아오면 안 된다.
6. 보관된 조각은 배치 사이에도 유지한다. 자동으로 비우거나 현재 조각으로 돌려놓지 않는다.
7. 조각 배열의 순서, 새 색 소개 정보, 뒤집힌 상태를 함께 보관·교환한다. 원본과 홀드·큐 배열을 공유하지 않는다.
8. 홀드로 `turn`, 점수, 콤보, `turnClears`, 붓기 예산, 구간 보너스, 활성 색상 또는 병 수가 바뀌면 안 된다. 빈 홀드 사용으로 조각 생성은 진행하지만 이는 성공한 배치가 아니다.
9. 이미 공개된 다른 미리보기는 유지한다. 새 색 소개 조각을 보관해도 색을 다시 해금하거나 소개용 조각을 중복 생성하지 않는다.
10. 미리보기 설정 0·1·2·3 모두 지원한다. 0일 때도 다음 조각은 결정적으로 한 번만 생성한다.

`canHold()`, `applyHold()` 같은 순수 엔진 함수를 기존 구조에 맞게 제공한다. UI·봇·테스트는 이 전이를 재사용하고 보관 규칙을 별도로 구현하지 않는다. 불가능한 홀드 요청은 상태를 바꾸지 않고 실패를 반환한다.

### 4.2 뒤집기와 되돌리기

뒤집은 조각의 보관으로 기존 횟수 제한을 우회하면 안 된다. 첫 구현에서는 다음 계약을 사용한다.

- 현재 조각의 `flipped` 정보가 홀드에 함께 이동한다. 눈에 보이는 물 순서를 보관 시 몰래 원상복구하지 않는다.
- 뒤집힌 보관 조각은 아직 사용하지 않은 뒤집기 1회를 예약한다. **그 조각을 실제 배치할 때 소비**한다.
- 아직 뒤집히지 않은 현재 조각을 뒤집을 수 있는지는 이미 소비한 횟수와 홀드의 예약 횟수를 함께 고려한다. 이미 뒤집힌 현재 조각을 다시 원래 순서로 돌리는 행동은 기존처럼 허용한다.
- 제한이 있는 규칙에서는 ‘이미 소비한 횟수 + 현재 뒤집기 예약 + 홀드 뒤집기 예약’이 한도를 넘지 않아야 한다. `flipLimit === 0`의 무제한 계약은 유지한다.
- 예: 한도 2회에서 A를 뒤집어 보관하고 B를 뒤집어 배치하면, A를 위해 남은 1회가 예약되어 있다. A를 그대로 배치하기 전에는 다른 조각에 새 뒤집기를 쓰지 못한다. 교환만으로 횟수가 추가 소비되거나 충전되지 않는다.
- 뒤집기 버튼의 가능 여부·남은 횟수·누름 표시가 실제 상태와 일치해야 한다. 홀드가 없는 과거 규칙의 표시와 동작은 유지한다.

성공한 홀드는 기존 행동 히스토리에 스냅샷을 남긴다. 기존 되돌리기 버튼으로 되돌리면 현재·보관 조각, 홀드 사용권, 큐·생성 번호, 소개 정보, 뒤집기 상태까지 원래대로 돌아와야 한다. 되돌리기 비용·사용 한도는 기존 정책을 따른다. 실패한 홀드나 렌더링은 히스토리를 만들지 않는다.

배치가 성공한 뒤 다음 조각의 패배 판정을 하기 **전에** 홀드 사용권을 갱신한다. 부활 자체로 홀드 사용권을 새로 주지 않는다. 종료·부활·새 판·모드 변경에서 기존 정책과 새 상태 초기화를 함께 확인한다.

## 5. 후반 3칸 조각 생성

### 5.1 첫 생성 정책

일반 병이 실제로 8개인 상태에서 **이후 새로 생성하는 조각**부터 3칸 확률을 적용한다. 기존 현재·보관·미리보기 조각은 변경하지 않는다. 점수만으로 아직 받지 않은 병을 얻었다고 추정하지 않는다.

첫 표준 후보는 다음과 같다.

| 항목 | 규칙 |
|---|---|
| 발생 확률 | 적격 일반 조각마다 5%. 비교 실험 후보로 10%도 사용 |
| 형태 | 50%는 AAA, 50%는 AAB·ABA·BAA 중 균등 선택 |
| 색 선택 | 활성 색상만 사용. 두 색 형태의 A와 B는 서로 다른 색 |
| 세 가지 서로 다른 색 ABC | 이번에는 생성하지 않음 |
| 새 색 소개 조각 | 기존 길이·소개 정책 유지. 3칸 확률 대상에서 제외 |

조각 배열의 순서와 물이 쌓이는 방향은 기존 엔진 계약을 따른다. AAA와 ABA처럼 뒤집어도 같은 조각의 뒤집기는 기존처럼 무효다.

3칸이 선택되지 않은 나머지 일반 조각은 기존 1~2칸 생성 정책을 따른다. 현재 표준의 최대 색상 이전 비율과 최대 색상 이후 `tailDoublePct: 90`을 유지한다. 즉 후반 5% 후보에서는 일반 조각 중 3칸 5%, 나머지 95%에서 기존 1칸/2칸 비율을 적용한다.

`pieceMax`를 일괄적으로 3으로 올려 1·2·3칸을 균등 추첨하지 않는다. 기존 `pieceMin/pieceMax`의 기본 생성 의미와 새로운 3칸 분기를 명확히 구분하고, 유효 조각 길이·예측 렌더링·저장 검증에는 새 분기를 반영한다.

### 5.2 결정성과 공정성

- 시드와 생성 번호를 사용하는 버전된 결정적 난수 정책을 사용한다. 게임 규칙에 `Math.random()`을 쓰지 않는다.
- 3칸 판정·형태용 난수는 기존 1~2칸 경로를 불필요하게 바꾸지 않도록 분리한다. 기능을 끈 기존 규칙은 원래 조각 순서와 결과를 그대로 재현해야 한다.
- 렌더링, 홀드 대안 확인, 예측, 봇 탐색이 실제 생성 번호나 큐를 소비하지 않는다.
- 같은 시드·규칙·행동 이력이면 저장 복원 전후에도 같은 결과를 얻는다.
- 빈 공간을 보고 들어갈 수 있는 3칸 조각만 뽑거나, 들어갈 곳이 없다는 이유로 작게 바꾸거나 건너뛰지 않는다.
- 3칸 조각은 하나의 병에 연속된 빈칸 3개가 필요하다. 여러 병에 흩어진 빈칸 합계로 배치를 허용하지 않는다.
- 확률과 형태 분포는 적격 일반 조각을 충분히 생성해 확인한다. 고정 시드 검증과 통계적 허용 오차를 사용하고, 소개 조각·8병 이전 조각을 표본에 섞지 않는다.

5%와 형태 가중치는 첫 실험값이다. 이번 비교에서 10%까지 평가할 수 있지만, 성장표·병 용량·색상 수·기존 점수 체계를 동시에 변경해 결과를 숨기지 마라.

## 6. 패배 판정과 탐색

현재 조각을 바로 넣을 수 없다는 이유로 즉시 종료하면 안 된다. 다음 분기를 기존 붓기 예산과 탐색 한도 안에서 확인한다.

1. 현재 조각을 바로 넣거나, 합법적인 붓기로 자리를 만들 수 있는가.
2. 홀드가 해금되어 있고 이번 배치 사이에 아직 사용하지 않았다면, 한 번의 보관/교환으로 얻을 조각을 바로 넣거나 붓기로 자리를 만들 수 있는가.

두 번째 분기의 후보는 보관된 조각, 또는 빈 홀드일 때의 실제 다음 조각 하나다. 0개 미리보기 설정에서는 복제 상태에서만 다음 조각을 확인한다. 미리보기의 더 먼 조각을 임의로 가져오거나 연속 홀드를 가정하지 않는다.

- `canMakeRoom()`의 `true / false / 'unknown'` 계약을 유지한다. 모든 합법적 분기가 확실히 불가능할 때만 종료한다. 탐색 한도에 도달한 `unknown`을 확정 패배로 취급하지 않는다.
- 같은 길이의 대안 때문에 동일한 보드 탐색을 불필요하게 반복하지 않는다. 기존 제한을 유지하고 전후 소요 시간을 확인한다.
- 성공한 붓기로 얻은 병 지급, 배치 후 홀드 재사용 가능 상태를 패배 판정에 반영한다.
- 홀드 가능 여부를 확인하는 과정에서 실제 상태를 변경하거나 화면 효과를 발생시키지 않는다.
- 홀드 사용 후에는 바뀐 현재 조각과 잠긴 사용권으로 다시 판정한다. 교환했다고 추가 붓기 예산을 주지 않는다.
- 홀드만으로 살 수 있는 판에서는 ‘병끼리 부으세요’만 안내하지 않는다. 홀드 또는 붓기 중 가능한 대응과 사용권 상태가 실제 규칙과 일치하게 표시한다.
- 이미 종료된 판의 홀드로 종료를 취소하거나, 잠긴 홀드를 대안에 포함하지 않는다.

## 7. 모바일 UI·조작·효과·다국어

### 7.1 화면 배치

현재 ‘지금/다음’ 조각 영역에 홀드를 통합한다. 병 영역과 아래 조작부 사이에 새 세로 줄을 추가하지 않는다. 작은 화면에서는 보조 문구와 미리보기 간격부터 정리한다.

- 6병 상태부터 홀드 영역의 자리를 확보해 7병 해금 때 기존 병·트레이가 밀리지 않게 한다. 잠금 안내는 작게 표현한다.
- 비어 있을 때 ‘보관’, 차 있을 때 ‘교환’, 사용한 뒤에는 ‘조각을 넣으면 다시 사용’이라는 의미가 읽혀야 한다.
- 보관된 조각의 색과 기존 색상 기호, 순서가 보여야 한다. 뒤집기 예약과 선택 가능 상태도 구분한다.
- 3칸 조각은 현재·다음·홀드의 **고정된 미리보기 높이 안에서** 읽히게 한다. 현재 조각 프레임이 높아져 병 높이가 줄거나 하단 버튼이 잘리면 안 된다.
- 같은 뷰포트·스킨·언어에서 수정 전후 병의 실제 렌더링 높이와 위치를 비교한다. 기존 6·7·8병 고정 배치를 유지한다. 약 390×844의 표준 화면에서 현재 일반 병은 약 136 CSS px 높이인 점을 참고하되 실제 기준선 수치를 먼저 측정한다.
- 터치 버튼은 최소 44 CSS px를 확보한다. 화면 밖 가로 스크롤이나 기본 페이지 세로 스크롤을 만들지 않는다.
- 현재 기본 블랙 테마, OS 밝은 모드에서도 어두운 기본 화면, `100dvh`·안전 여백·설정 창 내부 스크롤을 보존한다.
- 미리보기 0·1·2·3, 네 가지 병 스킨, 긴 번역, 큰 점수, 경고 배너에서도 겹침을 확인한다.

### 7.2 입력과 피드백

- 홀드는 명시적인 버튼으로 조작한다. 기존 탭/드래그 넣기와 병 사이 붓기를 유지한다.
- 버튼의 Enter/Space와 접근성 이름·비활성 상태를 지원한다. 전역 단축키를 추가한다면 기존 키와 충돌하지 않고 입력 필드·모달에서는 동작하지 않게 한다.
- 홀드 터치가 현재 조각 드래그나 병 배치로 전파되지 않게 한다. 교환 시 이전 조각의 드래그·선택·착지 예측을 안전하게 정리한다.
- 효과가 진행 중이어도 엔진 상태는 즉시 반영하고 빠른 연속 입력을 처리한다. 애니메이션 종료 콜백으로 조각을 교환하지 않는다.
- 보관/교환에는 짧은 이동·강조를 사용한다. 정리·큰 콤보 효과와 강도를 구분하고 홀드만으로 점수·콤보·화면 흔들림을 발생시키지 않는다.
- 3칸 전체의 드래그 표시, 착지 예측, 넣기 비행·타격, 뒤집기, 정리 연출을 확인한다. 세 번째 물칸이 사라지거나 기존 2칸 좌표를 사용하면 안 된다.
- 기존 효과 예산·정리 방식, 소리·진동 설정, 게임의 효과 줄이기와 OS `prefers-reduced-motion`을 유지한다. 전체/축소 효과에서 동일 입력의 최종 게임 상태가 같아야 한다.
- 새 판, 되돌리기, 창 숨김, 크기·언어·스킨 변경 때 잔상·타이머·이벤트가 누적되지 않게 한다.

한국어·영어·일본어·중국어 간체/번체·스페인어·브라질 포르투갈어·힌디어·인도네시아어의 **9개 언어**에 새 표시, 규칙 설명, 경고, ARIA 문구를 모두 추가한다. `messages.tsv`는 실제로 `|` 구분 형식이며 공백과 `{0}` 자리표시자 계약을 보존한다. `tr()`와 기존 빌드를 사용하고 생성된 i18n 스크립트를 직접 수정하지 않는다.

## 8. 저장·기록·회귀 경계

새 기능 상태는 최소한 보관 조각과 메타데이터, 홀드 사용권, 생성 정책 버전까지 복원할 수 있어야 한다. 기존 현재 조각·큐·생성 번호·성장 상태·뒤집기 예산과 함께 일관되게 다룬다.

- 홀드 사용 직전/직후, 7병·8병 해금 직후, 3칸 조각이 현재·큐·홀드에 있는 각각의 저장·새로고침·이어하기를 검증한다.
- 성공한 홀드와 배치·붓기의 되돌리기에서 해당 행동 이전의 전체 상태로 복원한다. 같은 행동 재실행으로 영구 보상·통계가 중복 지급되지 않는다.
- 복원할 조각의 길이·색 범위·형태·플래그를 확인한다. 손상된 새 저장을 정상 상태로 추정해 홀드를 몰래 비우거나 전체 기존 데이터를 지우지 않는다. 기존 오류 처리 흐름에 맞게 명확히 처리한다.
- 기능 필드가 없는 과거 저장, 구버전 일일 저장, 명시적 커스텀 규칙, 기본값 복원, 모드 전환, 핫 리로드를 확인한다.
- 언어·효과 설정 변경은 게임·큐·홀드·되돌리기 히스토리를 초기화하지 않는다.
- 홀드를 배치 턴이나 정리 성공으로 기록하지 않는다. 페이스 비교와 `turnLog`는 기존 배치 기준을 유지한다.
- 모의 클라우드 계약 검증과 실제 로그인·원격 쓰기 증거를 구분한다. 요청 없이 실제 계정 데이터를 바꾸지 않는다.

## 9. 구현 순서와 밸런스 비교

### 9.1 순서

1. 수정 전 행동·화면·성능 기준을 보존한다.
2. 홀드만 구현해 큐·패배·뒤집기·저장·입력 계약을 검증한다.
3. 홀드를 끈 조건에서 3칸 생성·배치·패배·화면을 검증한다.
4. 두 기능을 결합하고 동일 도구로 제한된 비교 실험을 수행한다.
5. 선택한 규칙으로 회귀 검증·브라우저 확인·보고까지 완료한다.

기능별 실험 상태를 사용자에게 별도 메뉴로 노출하지 않는다. 엔진의 규칙 설정과 재실행 가능한 비교 스크립트로 분리한다.

### 9.2 비교 실험

`research/expansion/bots.js`의 실제 엔진 전이와 기존 1수/2수 붓기 탐색 정책을 재사용한다. 새 홀드 상태를 깊은 복사에 포함하고, 합법적인 ‘홀드 없이 배치’와 ‘홀드 후 배치’ 후보를 고려한다. 현재 조각만 고려하는 기존 봇 결과로 홀드 효용을 판단하지 마라.

후보 탐색은 실제 `applyHold/applyFlip/applyPour/applyPlace`의 결과와 일치해야 한다. 후보 생성에서 실제 큐를 소비하거나, 무한 교환·무료 뒤집기·홀드 사용권 초기화를 허용하면 안 된다. 상태 캐시를 사용한다면 홀드·사용권·큐·관련 메타데이터를 키에서 누락하지 않는다.

첫 비교는 같은 `expansion-0`~`expansion-59` 시드 목록, 정책별 최대 500배치, 임시 잔·부활 없이 다음 조건으로 수행한다.

| 조건 | 홀드 | 3칸 확률 |
|---|---|---:|
| 현재 기준 | 없음 | 0% |
| 홀드 단독 | 7병에서 해금 | 0% |
| 3칸 단독 A/B | 없음 | 5% / 10% |
| 결합 A/B | 7병에서 해금 | 5% / 10% |

기능별 조건에서 탐색 정책과 계산 자원을 공정하게 유지하고 한도를 보고한다. 같은 시드라도 홀드로 큐 소비와 점수 성장 시점이 달라져 공급 조각이 완전히 같지는 않다.

기존 결과 파일에는 2수 탐색 정책의 현재 기준이 60시드 중 42개에서 500배치 상한에 도달한 기록이 있다. 이는 과거 자동 실험이다. 현행 도구로 재현해 기준값을 확인하고 사람의 숙련도나 플레이 시간으로 해석하지 않는다.

보고할 지표:

- 종료 배치 수·점수의 중앙값/상위 분위수, 500배치 생존 비율.
- 7병·8병 도달률과 도달 배치 수, 8병 이후 배치 수.
- 배치당 붓기·홀드 사용 수, 홀드 덕분에 패배를 피한 경우, 보관 조각을 장기간 그대로 두는 경우.
- 실제 3칸 생성·배치 비율, 3칸 때문에 막힌 경우와 홀드/붓기로 대응한 경우.
- 각 탐색 정책의 연산량·시간, `unknown` 비율과 잘못된 조기 종료 여부.

500배치 생존이 많은 조건은 동일 정책으로 살아남은 첫 6시드 등을 최대 1,500배치까지 추가 확인한다. 이는 조건부 표본이며 전체 생존율로 확대 해석하지 않는다. 상한 도달 결과는 ‘≥500배치’처럼 표시한다.

홀드만으로 이미 긴 판이 더 길어지는지, 3칸이 준비 가능한 압박인지 단순한 막힘인지 확인한다. 5%와 10% 중 근거가 있는 후보를 선택한다. 차이가 불분명하면 5%를 보수적인 첫 구현값으로 남기고 불확실성을 보고한다. 둘 다 문제가 있으면 기능을 플레이 가능한 실험본으로 완성하되 출시 준비 완료라고 선언하지 않는다. 관련 없는 규칙을 함께 바꾸거나 사람의 재미를 봇 수치로 입증하지 마라.

## 10. 필수 기능·브라우저 검증

기존 검사를 수정 전에 실행해 원래 실패와 새 회귀를 구분한다. 필요한 새 검사는 `research/hold-triple/`와 `uitest/hold-triple.js` 등에 기존 방식으로 추가한다. 단순 구현 복사 테스트보다 규칙의 경계와 실제 전이 결과를 확인한다.

최소 엔진 검증:

1. 6병 잠금, 7병 해금, 빈 보관·교환·한 배치 사이 두 번째 홀드 거부, 성공한 배치만 사용권 복구.
2. 빈 홀드의 큐 이동·보충 1회, 교환의 큐·생성 번호 불변, 미리보기 0~3, 실패 요청의 전체 상태 불변.
3. 홀드의 점수·턴·붓기·구간·성장 불변, 소개 조각 보관·재교환, 배열 참조 분리.
4. 뒤집기 예약·배치 시 소비·원복·무제한·한도 경계, 홀드로 예산을 우회하지 못하는 행동 이력.
5. 홀드만으로 살아남는 보드, 잠긴 홀드로는 살 수 없는 보드, 붓기와 교환의 결합, `unknown`과 확정 패배 구분.
6. 8병 직전/직후 생성, 기존 큐 불변, 3칸 형태·색·확률, 소개 조각 예외, 3칸 분산 빈 공간 거부.
7. 3칸 넣기·정리·콤보·뒤집기, 동일 시드/행동 재현, 저장·되돌리기·재실행 일치.
8. 구버전·일일·커스텀 규칙의 조각·행동·서명 동치, 새 기록 분리·표준 보상·기본 설정 전환.

관련 기존 명령을 현재 도구에 맞게 실행한다. 이번 변경에 직접 영향을 받는 기대값은 근거와 함께 수정하고, 관련 없는 실패를 숨기기 위해 검사를 삭제하거나 허용 범위를 늘리지 않는다.

```powershell
node test-v2.js

node uitest/i18n.js

git diff --check
```

새 기능 검사와 비교 실험 명령도 보고서에 정확히 남긴다. 과거 엔진 해시 동일 검사를 새 기준값으로 바꾸는 것으로 회귀 검증을 대체하지 않는다.

브라우저는 `build-pages.js`로 생성한 정상 문서에서 확인한다.

- 최소 `360×640`, `390×844`, `412×915`, `768×1024`의 6·7·8병과 2칸/3칸 현재·보관 조각을 확인한다.
- 짧은 화면·안전 여백 조합도 기존 모바일 검사에 맞춰 재현한다. 특히 `360×600` 및 `390×724`에서 플레이 영역과 하단 조작부가 안전 여백 안에 있는지 측정한다.
- 네이티브 터치·마우스·키보드로 보관→잠금→배치→교환, 교환 직후 빠른 드래그·취소·되돌리기·새로고침을 확인한다.
- 효과 전체/축소, OS 밝음/어두움, 스킨·언어 변경, 설정 창 내부 스크롤을 확인한다. 병·현재 조각·홀드·미리보기 겹침과 기본 페이지 스크롤이 없어야 한다.
- 7병 해금 뒤 홀드를 사용하고, 8병 이후 자연 생성된 3칸 조각을 처리하는 경로를 시드 기반 실제 UI 입력으로 최소 한 번 재생한다.
- 상태 주입 경계 검증, 자동 전략의 UI 재생, 직접 사람의 플레이를 구분한다. 휴대폰 크기 Chrome 검증을 실제 Android/iPhone 검증으로 표현하지 않는다.

## 11. 산출물과 완료 보고

- 실제 게임 수정본, 9개 언어 메시지, 필요한 회귀·브라우저 검사.
- `research/hold-triple/REPORT.md`: 기준 커밋·소스, 최종 규칙, 뒤집기 예약·저장·기록 정책, 명령과 결과, 후보별 비교, 선택 근거, 남은 불확실성.
- `research/hold-triple/out/`: 재현 가능한 작은 JSON 결과와 시드·규칙. 큰 이미지·임시 파일은 기존 `outputs/hold-triple/` 관례를 따른다.
- 전후 병 크기·좌표, 대표 보관/교환/3칸 화면, 효과 진행 중 입력의 증거.
- `docs/ROADMAP.md`에 실제 완료한 범위와 미검증 사항만 추가한다. 과거 증거를 덮어쓰지 않는다.

배포가 실행 요청에 포함되어 있으면 기존 `deploy-pages.ps1`, `scripts/verify-pages.js`와 `research/mobile-viewport/verify-public.js`를 확인해 사용한다. 공개 URL의 `version.json` 소스 커밋과 실제 HTML/에셋이 배포 커밋에 일치하는지 확인한다. HTTP 200만으로 최신 반영이라고 보고하지 않는다.

마지막 보고는 한국어로 작성한다. 두 기능의 실제 동작, 최종 해금·확률·형태, 자동/브라우저 검증, 실행 주소 또는 실행 방법, 배포 여부와 남은 판단을 간결하게 설명한다.

출시 전 사람의 체험에서 확인할 질문은 세 가지로 좁힌다: ‘홀드가 선택을 늘렸는가, 입력을 늦췄는가’, ‘3칸 조각을 준비해서 받아낼 수 있었는가’, ‘8병 이후에도 다시 최고 기록에 도전하고 싶었는가’.
