# 점수에 따라 판이 커지는 무한모드 구현 프롬프트

작성: 2026-10-08. 대상 프로젝트: `C:/workspace/water-sort-survival`.
권장 실행 모델: **GPT-6.1 Sol / Extra high (xhigh)**.

이 문서는 구현 작업 지시다. 현재 코드를 확인한 다음 실제 수정, 자동 검증, 브라우저 확인, 비교 결과 정리까지 진행해라. 계획만 작성하고 끝내지 마라. 세부 수치는 아래 원칙 안에서 근거를 갖고 결정하되, 사람의 플레이로 확인하지 않은 재미나 출시 가능성을 입증했다고 말하지 마라.

## 1. 이번에 만들 경험

이 게임의 중심은 무한모드에서 빠르게 물을 정리하고 콤보를 이어 최고 기록에 도전하는 경험이다. 점수를 올리면 사용할 색이 늘어나고, 일정 점수에서는 **용량 4칸짜리 일반 빈병이 하나씩 추가**된다. 아래쪽 여섯 병을 익힌 뒤 위쪽으로 판이 확장되면서 더 많은 병을 관리하게 만든다.

색상 증가는 압박, 새 병은 숨통이 트이는 보상이 되어야 한다. 병을 추가한 뒤에도 정리하고 판단할 일이 계속 생겨야 한다. 단순히 플레이 시간만 늘어나거나 병을 찾아다니는 수고가 늘어난다면 실패한 설계다.

첫 구현 범위는 다음과 같다.

- 시작: 일반 병 6개, 병당 4칸, 색상 4개.
- 성장: **점수 기준으로 색상 증가와 7번째·8번째 병 해금**. 두 줄까지 확장한다.
- 한 판에서 해금한 일반 병은 게임이 끝날 때까지 유지한다. 새 판은 다시 6개에서 시작한다.
- 초기 실험의 최대 병 수는 8개다. 색은 현재 팔레트와 기호 체계 안에서 최대 8~9개를 검토한다.
- 병 수와 색 수를 무조건 일대일로 늘리지 않는다. 두 증가 시점을 함께 조정한다.
- 새 무한모드를 직접 플레이할 수 있게 완성한다. 기존 규칙은 과거 저장 복원과 개발 비교용으로 유지한다. 사용자에게 별도의 클래식 모드 선택 화면을 추가할 필요는 없다.

이번에는 스테이지 모드, 타이머, 자동 낙하, 장애물, 새 재화, 스킬, 광고 SDK, 엔진 이식, 대규모 시각 개편을 추가하지 않는다. ‘테트리스 같은 느낌’은 기록 도전과 숙련에 따른 빠른 정리라는 목표이며 실시간 제한을 새로 넣으라는 뜻은 아니다.

현재 구현에서 특히 확인할 점:

- 기본 색상 증가는 `colorsAt()`의 턴 기준이며, `pieceAt(seed, rules, i)`는 시드와 조각 번호로 결정된다.
- UI 미리보기도 `pieceAt()`를 직접 호출한다. 점수 기반으로 바꾸면서 이미 보여 준 조각을 다시 계산하면 안 된다.
- `applyPlace()`뿐 아니라 `applyPour()`의 정리에서도 점수가 오른다.
- `settle()`, `zoneBreak()`, `checkStuck()`의 호출 순서가 점수·병 해금·패배 판정에 영향을 준다.
- `zoneAt()`, 구간 보너스, 새 색 소개 조각, 별 보상은 현재 턴 기반 색상 증가와 연결되어 있다.
- `rulesSig()`, 최고점, 페이스 비교, 별 획득 자격, 로컬 저장, 계정 동기화를 함께 확인해야 한다.
- `.rack`, 드롭 대상 판정, 키보드 이동, 콤보 효과 배치에 한 줄 선반 가정이 남아 있을 수 있다.

현재 구조를 재사용하고 필요한 범위만 바꿔라. 기존 미추적 프롬프트를 수정·삭제·이동·커밋하지 마라. 신규 라이브러리는 도입하지 않는다.

## 3. 성장 규칙과 엔진 계약

### 3.1 점수 성장표

점수 임계값, 목표 색상 수, 목표 병 수를 **한 곳의 명시적인 표**로 관리한다. UI, 엔진, 봇이 서로 다른 표를 사용하면 안 된다. 초안으로 아래 순서를 검토하되, 점수 임계값과 병 지급 간격은 현재 점수 분포와 비교 실험으로 정한다.

| 성장 순서 | 목표 색상 수 | 일반 병 수 | 의도 |
|---|---:|---:|---|
| 시작 | 4 | 6 | 규칙과 정리 리듬에 적응 |
| 첫 압박 | 5 | 6 | 기존 공간을 관리하게 함 |
| 첫 확장 | 6 | 7 | 위쪽 새 병으로 대응 공간 제공 |
| 두 번째 압박 | 7 | 7 | 확장된 판에서도 정리 필요 |
| 두 번째 확장 | 8 | 8 | 위쪽 두 번째 병 해금 |
| 선택적 후반 후보 | 9 | 8 | 8색에서 지나치게 안정화되는 경우만 비교 |

이 표는 첫 후보이며 최종 밸런스 판정이 아니다. 색상 추가와 병 지급 사이에 짧은 간격을 두는 후보도 비교할 수 있다. 어느 경우든 첫 병 확장이 체험하기 어려울 만큼 늦거나, 너무 이르게 주어져 초반 정리가 의미 없어지지 않는지 확인한다.

최대 확장 뒤에도 최고 기록 도전은 계속된다. 색과 병을 끝없이 추가하지 않는다. 먼저 성장표를 조정하고, 그래도 후반이 지나치게 쉬운 경우에만 기존 1~2칸 조각의 생성 비율 조정을 작은 추가 후보로 검토한다. 여러 난도 변수를 한꺼번에 바꾸지 마라.

### 3.2 행동 처리 순서와 큰 콤보

- 성공한 넣기·붓기에서 기존 점수 정산을 마친 뒤 해금 조건을 확인한다. 실패한 입력, 단순 렌더링, 드래그 중에는 성장 상태를 변경하지 않는다.
- 점수로 획득한 병은 **같은 행동의 패배 판정 전에** 빈 일반 병으로 추가한다. `applyPlace()`만 처리해서 붓기로 얻은 해금을 놓치지 마라.
- 한 번의 큰 점수 획득으로 병 임계값 두 개를 모두 넘으면 획득한 병은 모두 반영한다. 등장 연출은 순서대로 보여 주되, 연출 때문에 사용 가능한 병이나 입력을 잠그지 않는다.
- 색상 목표는 점수표로 결정하지만 실제 활성 색상은 **성공한 배치 1회당 최대 1색**만 증가시킨다. 붓기로 높아진 목표는 다음 배치에서 반영한다. 큰 콤보 직후 여러 낯선 색이 한꺼번에 생성되지 않게 한다.
- 이미 화면에 나온 현재 조각과 미리보기는 유지하고, 이후 새로 생성하는 조각부터 활성 색상을 적용한다. 따라서 해금 시점과 새 색이 실제 도착하는 시점은 다를 수 있다. 안내는 이 차이를 정직하게 표현한다.
- 해금 자체에는 점수를 주지 않는다. 해금 → 보너스 → 해금이 같은 행동에서 재귀적으로 반복되지 않게 한다.
- 종료된 게임에 병을 사후 지급해 자동 부활시키지 않는다. 기존 부활 기능과 병 해금은 구분한다.

### 3.3 조각 생성, 정산, 임시 잔

- 확장형에서는 현재 조각과 확정된 미리보기 큐, 생성 번호, 활성 색상, 성장표 버전을 상태에 보존한다. 시드·같은 규칙·같은 행동 이력은 같은 상태를 만들어야 한다.
- 렌더링, 예측 표시, 봇 탐색이 생성 번호나 실제 큐를 소비하지 않게 한다. 봇은 복제 상태에서 실제 엔진의 전이를 사용한다.
- 확장형과 과거 규칙의 조각 생성 경로를 명확히 구분한다. 과거 일일 도전의 `pieceAt()` 계약을 임의로 바꾸지 마라.
- 이번에는 기존 턴 단위 구간 정산·별 보상 구조를 가능한 한 유지하고, 색상 증가와 새 색 소개만 점수 성장과 분리해 연결한다. 정산 보너스는 그 행동에서 새 병을 주기 전의 보드로 계산한다. 새 병 지급만으로 같은 정산에서 추가 빈병 보너스를 얻지 않게 한다.
- 기존 턴 경계에서 새로운 색을 강제 생성하는 `zoneTwin` 동작을 확장형에 그대로 적용하지 않는다. 새 색 소개 조각을 유지한다면 해당 색 활성화 이후 아직 공개하지 않은 큐 항목에만 한 번 반영한다.
- HUD의 색 수, 다음 변화 안내, 정산 알림이 서로 모순되지 않아야 한다. 기존 턴 기반 설명을 실제 동작에 맞게 수정한다.
- 새 병은 기존 병과 동일하게 넣기·붓기·정리·점수를 모두 지원한다. `spare` 또는 용량 1칸짜리 임시 잔을 확장 병으로 재활용하지 않는다.
- 확장형 첫 실험에서는 임시 잔 제안을 끈다. 기존 저장·과거 규칙의 임시 잔 구현과 사용자 설정은 보존한다. 밸런스 비교에서는 모든 후보의 부활·임시 잔 사용을 동일하게 끈다.

## 4. 두 줄 배치와 조작감

- 기존 6개 병은 아래 줄에 고정한다. 7번째와 8번째 병은 위 줄의 미리 정한 자리에 각각 추가한다.
- 병이 늘어났다고 기존 병을 가운데로 다시 정렬하거나 작게 축소하지 않는다. 7번째 병도 8번째 해금 때 위치가 바뀌지 않게 한다.
- 위쪽 공간을 미리 확보하되 잠긴 빈 슬롯 여러 개로 화면을 복잡하게 만들지 않는다. 다음 병 목표는 간결한 표시 하나로 전달한다.
- 작은 화면에서도 병 터치 영역은 최소 44 CSS px를 목표로 확보한다. 화면 폭이 부족하면 간격과 여백부터 조정한다.
- 두 줄의 실제 좌표로 드롭 대상을 판정한다. 가로 위치만 보고 다른 줄의 병을 고르거나, 두 줄 사이 빈 공간을 엉뚱한 병으로 흡수하면 안 된다.
- 현재 기본 조작, 선택적 `tapPlace`, 컵 끌기, 병 사이 끌기, 취소, 되돌리기, 키보드 조작을 유지한다. 새 병도 같은 경로로 조작한다.
- 판 확장으로 콤보 배지, 버스트, 점수, 다음 조각이 겹치지 않도록 효과 위치를 조정한다. 최근 구현한 효과의 강도·기본값·설정을 임의로 되돌리지 않는다.
- 병 해금은 짧고 눈에 띄게 보여 주되 모달이나 확인 버튼을 요구하지 않는다. 빠르게 연속 조작할 수 있어야 한다.
- ‘다음 병까지 N점’, ‘다음 색까지 N점’ 중 가까운 변화를 명확히 보여 준다. 색상은 색뿐 아니라 기존 기호로도 구별한다.

브라우저에서 최소 `360×740`, `390×844`, `412×915`, `768×1024`를 확인한다. 플레이 영역의 잘림, 가로 스크롤, 버튼 겹침, 트레이와 선반 충돌을 검사한다. 화면 회전이나 크기 변경 때 입력 대상 좌표도 갱신되어야 한다.

## 5. 저장과 기록 호환성

- 새 규칙에 별도 버전/서명을 둔다. 확장 여부, 성장표 및 생성 정책이 기록 비교에 반영되어야 한다. 실제 병이 해금될 때마다 기록 키가 바뀌는 구조는 피한다.
- 과거 최고점·페이스·별·테마·설정을 삭제하지 않는다. 난도가 달라진 최고점을 같은 기록으로 비교하지 않는다. 계정 동기화에서도 새 기록이 과거 키를 덮어쓰지 않게 한다.
- 진행 중인 기존 저장은 기존 규칙으로 이어 할 수 있게 한다. 새로 시작하는 무한모드에서 새 규칙을 적용한다. 명시적인 사용자 커스텀 규칙이 있으면 강제로 초기화하지 말고 적용 정책을 설명한다.
- 현재 일일 도전은 기존 규칙과 날짜별 같은 조각 순서를 유지한다. 점수 기반 분기를 무작정 적용하면 플레이어마다 순서가 달라지므로 이번 범위에서 함께 전환하지 않는다.
- 새 표준 무한모드에 다른 `rulesSig()`가 생겼다는 이유만으로 기존 별 획득 자격 검사에서 보상이 전부 막히지 않게 확인한다. 기존 보상량을 별도로 늘리지 않는다.
- 저장·새로고침·이어하기·되돌리기에서 병 수, 병 내용, 활성 색상, 대기 중인 색상 증가, 현재 조각, 큐, 생성 번호, 성장 이력을 함께 복원한다.
- 해금 직후 되돌리면 이전 보드와 성장 상태로 돌아가야 한다. 그 행동을 다시 수행해도 영구 보상이나 통계가 중복 지급되지 않아야 한다.
- 기존 커스텀 규칙 설정과 디버그/핫 리로드 경로도 확인한다. 새 필드가 없는 과거 저장을 새 규칙으로 추정해서 읽지 마라.

## 6. 비교 실험과 검증

### 6.1 제한된 밸런스 실험

먼저 수정 전 기본 규칙의 기준값을 현재 도구로 재현한다. 이후 최대 3개의 성장표 후보를 같은 시드 목록과 동일한 봇 정책으로 비교한다. `harness.js`와 `bot2.js`의 탐색 수준이 다른 두 정책을 활용하되, 확장 상태와 미리보기 큐를 올바르게 다루도록 필요한 어댑터를 만들거나 수정한다.

첫 비교는 후보별·봇별 60시드, 최대 500배치로 시작한다. 살아남은 판이 많으면 일부 동일 시드를 더 긴 상한으로 확인한다. 큰 탐색으로 시간을 소모하기보다 상위 후보를 고르고 조정은 3회 이내로 제한한다. 확정하기 어려우면 가장 타당한 후보를 플레이 가능한 상태로 남기고 불확실성을 보고한다.

보고할 지표:

- 종료까지 배치 수와 점수의 중앙값·상위 분위수, 실험 상한 생존 비율.
- 첫 번째·두 번째 병 해금 도달률 및 도달 배치 수.
- 첫 정리까지 배치 수, 최대 콤보, 배치당 붓기 수.
- 확장 전후 여유 칸, 즉시 가능한 배치 대상 수, 종료 시 병 수·색 수.
- 최대 확장 이후 단순 색상별 병 배정으로 장기 생존이 고착되는지 여부.

판정 원칙:

- 상한까지 살아남았으면 ‘500배치 생존’ 또는 ‘중앙값 ≥500’처럼 표시한다. 실제 종료 시간을 안다고 쓰지 않는다.
- 점수에 따라 색상 수가 달라지므로 같은 시드를 썼어도 서로 다른 규칙의 조각 내용이 같다는 뜻은 아니다. 시드 목록과 결정성을 통제했다는 범위로 설명한다.
- 예전에 기존 색상 곡선을 유지한 채 빈병만 늘린 실험은 이번 결합 설계의 결론으로 사용하지 않는다. 비교하려면 재현 가능한 스크립트와 결과를 남긴다.
- 생존 시간 증가 자체를 개선으로 보지 않는다. 확장 도달 가능성과 후반 긴장감, 조작 부담을 함께 본다.
- 봇 수치를 사람의 실력·재미·플레이 시간으로 환산하지 않는다. 자동 검증은 규칙 결함과 극단적인 밸런스 문제를 찾는 근거다.

### 6.2 기능 회귀 검증

기존 테스트를 먼저 실행해 수정 전 실패를 구분한다. 실패를 없애기 위해 관련 없는 기대값을 약화시키지 마라. 새 규칙에서는 적어도 아래 경계를 실제 엔진으로 검증한다.

1. 6병·4색 시작, 점수 임계값 직전/일치/초과, 7병/8병 및 최대 색상 상한.
2. 넣기와 붓기 각각으로 점수를 얻어 병을 해금하는 경우.
3. 새 병 덕분에 계속 둘 수 있는 행동이 해금 전에 패배로 처리되지 않는 경우.
4. 큰 콤보로 여러 임계값을 넘은 경우의 병 지급과 배치당 1색 증가.
5. 공개된 현재 조각·미리보기 불변, 새 색 도입, 예측·렌더링의 상태 불변.
6. 같은 시드·행동 재현, 봇 후보 탐색과 실제 전이 일치.
7. 확장 직전/직후 저장 복원·되돌리기, 보상 중복 방지.
8. 과거 저장, 과거 기록 키, 커스텀 규칙, 일일 도전 순서의 호환성.
9. 새 병의 넣기·붓기·정리·뒤집힌 조각 배치·패배 판정 참여.
10. 두 줄에서 연속 탭·드래그·취소·크기 변경과 효과 도중 입력.

### 6.3 실행 화면 확인

`build-pages.js`가 생성한 정상 HTML 문서로 브라우저를 실행한다. 원본 HTML 조각을 바로 열어서 생기는 모달 표시 문제를 제품 결함으로 오인하지 마라.

6병, 7병, 8병 상태의 화면과 실제 입력을 확인한다. 빠른 연속 입력 및 `reduceFx` 설정도 확인한다. 테스트 전용 상태 주입을 썼다면 그 사실을 구분하고, 자연스럽게 플레이해서 해금까지 간 경로도 최소 하나 확인한다.

휴대폰 크기 브라우저 검증과 실제 휴대폰 터치 체험은 구분한다. 실제 기기로 체험하지 않았다면 미검증으로 남긴다.

## 7. 산출물과 완료 보고

- 실제 플레이 가능한 수정본과 필요한 회귀 검증.
- `research/expansion/` 아래 재실행 가능한 비교 스크립트, 작은 결과 파일, `REPORT.md`.
- `REPORT.md`에 기준 커밋, 명령, 시드, 후보별 표, 최종 성장표와 선택 근거, 저장 호환 정책, 브라우저 확인 범위 및 한계를 기록한다.
- `docs/ROADMAP.md`에서 이번에 실제 달성한 범위만 갱신한다. 과거 작업 기록은 덮어쓰지 않는다.
- 마지막 보고는 한국어로 작성한다. 핵심 변경, 선택한 병/색상/점수표, 검증 결과, 직접 실행 방법, 남은 판단을 간결하게 설명한다.
- 실제 사람의 후속 체험에서 확인할 질문은 세 가지로 좁힌다: ‘새 병을 얻고 계속하고 싶었는가’, ‘두 줄에서도 빠르게 조작했는가’, ‘확장 이후에도 정리 선택이 흥미로웠는가’.

이번 작업의 완료는 **제한된 확장형 무한모드를 구현하고 비교 가능한 상태로 만드는 것**이다. 출시 성공이나 재미를 자동 테스트 통과로 단정하지 마라. 요청 범위는 로컬 구현과 검증이며 공개 배포·푸시는 포함하지 않는다.
